# AGENTS.md for Terraform Project

This file provides instructions for AI coding agents working on this Terraform module.

## Project Overview

This module manages app registrations in Microsoft Entra ID (Azure AD) using the `hashicorp/azuread` provider. It supports:

- An app registration (`azuread_application`).
- An optional enterprise application, i.e. the service principal (`azuread_service_principal`).
- An optional client secret with a user-defined expiration date (`azuread_application_password`). The secret value is generated by Entra ID and exposed through a sensitive output.
- Optional federated identity credentials (`azuread_application_federated_identity_credential`) to authenticate workloads (HCP Terraform, GitHub Actions, Kubernetes, etc.) without secrets.

### Required Files and Directories

- `main.tf` – Resource and data source definitions.
- `outputs.tf` – Output value definitions (alphabetical order).
- `README.md` – Generated using Terraform-Docs. Do not edit manually.
- `variables.tf` – Input variable definitions (alphabetical order with required variables at the top).
- `versions.tf` – Terraform version and provider requirements. A reusable module must not contain a `providers.tf` file or provider configuration blocks.
- `docs/README_header.md` – Describe the purpose of the module, permissions, authentication, features and a usage example.
- `docs/README_footer.md` – Provide links to the external documentation used to generate the code.
- `tests/` – Native Terraform tests (`.tftest.hcl`) using `mock_provider "azuread"`; no real Entra ID tenant is required.

## Tools and Frameworks

- Run `terraform fmt -recursive` before every commit.
- Run `terraform validate` and `terraform test`.
- Use TFLint (`.github/linters/.tflint.hcl`) and markdown-lint for static analysis.
- Use Terraform-Docs with `.github/terraform-docs/.tfdocs-config.yml` to generate `README.md`.

## Code Formatting

- Indent two spaces for each nesting level.
- Align equals signs when multiple single-line arguments appear consecutively.
- Place arguments at the top of blocks, followed by nested blocks separated by one blank line.
- Put meta-arguments (`count`, `for_each`) first, then other arguments, then nested blocks.
- Place `lifecycle` blocks last.
- Separate top-level blocks with one blank line.

## Resource Naming

- Use descriptive nouns separated by underscores.
- Do not include the resource type in the resource name.
- Wrap resource type and name in double quotes.
- Example: `resource "azuread_application" "main"` not `resource "azuread_application" "azuread_application_main"`.

## Variables and Outputs

- Define `type` and `description` for every variable.
- Include reasonable `default` values for optional variables; prefer `optional()` attributes with defaults inside object variables.
- Set `sensitive = true` for secrets.
- Order variable parameters: type, description, default, sensitive, validation blocks.
- Order output parameters: description, value, sensitive.
- Validate inputs with meaningful error messages (GUID format for object IDs, RFC 3339 for dates, `https://` issuers, allowed `sign_in_audience` values).

## Dynamic Resource Management

- Use `count` with conditional expressions for single optional resources (e.g. the enterprise application, the secret).
- Use `for_each` over maps for repeatable resources (e.g. federated credentials).
- Add comments above resource blocks to explain non-obvious logic.

## Comments and Documentation

- Use `#` for comments (not `//` or `/* */`).
- Write self-documenting code; comment only to clarify complexity.

## README_header.md

- Describe the general purpose of the module.
- A `Permissions` section listing the Microsoft Graph application permissions (e.g. `Application.ReadWrite.All`) or Entra ID roles (e.g. `Application Administrator`) required by the identity running Terraform.
- An `Authentication` section describing how the `azuread` provider authenticates (e.g. OIDC / dynamic credentials, `ARM_*` environment variables).
- A `Features` section listing the key capabilities.
- A `Usage example` section with a realistic module call.

## Version Management

- Pin Terraform using `required_version`.
- Constrain provider versions in `required_providers` with the pessimistic operator (e.g. `~> 3.10.0`).
- Avoid open-ended constraints (`>`, `>=` without an upper bound) for providers.

## Security and Secrets

- Never commit `terraform.tfstate` files, `.terraform` directories or `.tfvars` files containing secrets.
- Mark secret outputs and variables as `sensitive = true`.
- Prefer federated credentials over client secrets; document that client secrets are stored in the Terraform state, which must be protected (e.g. HCP Terraform remote state).
- Always require an explicit expiration date for client secrets; never create non-expiring secrets.
- Use least privilege for the identity running Terraform and for the app registration itself.
- Use dynamic provider credentials and environment variables for provider authentication.

## Testing

- `tests/variables.tf.tftest.hcl` – one `run` per validation rule using `expect_failures`.
- `tests/main.tf.tftest.hcl` – behavior tests (resource counts, outputs) using `mock_provider "azuread"`.

## State Management

- Use HCP Terraform remote state storage.
- Do not configure backend blocks inside the module.
